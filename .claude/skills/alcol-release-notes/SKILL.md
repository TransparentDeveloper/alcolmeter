# Release Notes — 양조장 밤일지 톤

alcolmeter의 각 서브프로젝트(web · extension · domain · design-system) 변경 이력을
**읽고 싶어지는 한 편의 짧은 이야기**로 씁니다.
도입부의 익살스러운 서사가 호기심을 끌고, 그 아래 변경점이 또렷하게 이어집니다.

## 결과물 — 서브프로젝트별 CHANGELOG

릴리즈는 **서브프로젝트 단위**입니다. 각자 자기 CHANGELOG를 가집니다.

| 서브프로젝트 | CHANGELOG 경로 | 태그 prefix |
|---|---|---|
| web | `apps/web/CHANGELOG.md` | `web-v{SemVer}` |
| extension | `apps/extension/CHANGELOG.md` | `extension-v{SemVer}` |
| domain | `packages/domain/CHANGELOG.md` | `domain-v{SemVer}` |
| design-system | `packages/design-system/CHANGELOG.md` | `design-system-v{SemVer}` |

- **어느 서브프로젝트인지 판별:** 어떤 패키지의 버전이 범프됐는지 / 변경이 어느 디렉터리에 있는지 / (릴리즈라면) 만들 태그의 prefix로 정합니다.
- GitHub Release는 **태그가 서브프로젝트를 식별**합니다(`web-v0.4.0`, `domain-v0.5.0` 등). Release 본문 = 그 CHANGELOG의 해당 버전 섹션.
- 형식: Keep a Changelog. **최신 버전이 맨 위.**
- 라이브러리(domain·design-system)는 독자가 개발자이므로, 불릿은 API·토큰·타입 등 **소비처가 체감할 변화**를 명확히. 플레이버(시점·계절)는 동일하게 적용합니다.

## 목소리 (이 스킬의 심장)

네 가지가 동시에 성립해야 합니다.

1. **전부 존댓말.** 인용문도, 불릿도 예외 없이. (양조장 노장이 손님에게 들려주듯)
2. **인용문 = 익살스러운 "도착 알림", 불릿 = 정보.** 인용문은 풍경 묘사로만 끝내지 말고 *이번 판이 왔다*를 익살스럽게 알립니다(아래 「인용문은 *도착을 알린다*」 참고). 변경 불릿은 멋을 부리되 *읽으면 뭐가 바뀌었는지 바로* 압니다. 변경 이력의 본분은 "무엇이 바뀌었나" 전달이라, 분위기에 정보가 묻히면 실패입니다.
3. **세계관·유머 결:** 양조장 장인의 밤일지 + 발효·측정·전통주 판타지. 유머는 **진지하고 차분한 문장에 마지막 한 끗으로 피식 나는 건조한 위트(deadpan)**입니다. 깔깔대는 개그나 과한 보라색 산문은 금물. 웃기려 들지 말고 점잖게 한 번 비트는 정도로, 보통 마지막 문장에 슬쩍 얹습니다.
4. **압축. 주저리주저리 금지.** 인용문은 1~2문장, 불릿은 한 줄로 핵심만 남기고 군더더기 형용사·반복 설명은 덜어냅니다. 멋이 정보를 늘려선 안 됩니다. 짧을수록 좋습니다.

## 인용문은 *무엇이 바뀌었나*를 익살스럽게 알린다 (내용이 주인공)

인용문의 본분은 **이번 판에서 뭐가 바뀌었는지를 위트 있게, 도착과 함께 알리는 것**입니다. **변경 내용이 주인공이고, 시점·계절은 곁들이는 양념**입니다. 계절 풍경부터 깔고 시작하면(예: "긴 해가 기우는 저녁, …") 정작 *무엇이 왔는지*가 뒤로 밀려 밋밋해집니다.

**공식:** `[업데이트 내용을 익살스럽게 전하는 도착 선언]`(필수) `+ [시점·계절 양념]`(선택)

- 핵심은 *무엇이 바뀌었나*를 위트로 푸는 것입니다. 예: "용어 풀이를 읽다 '이건 좀 아닌데' 싶을 때, 그 한마디를 곧장 띄워 보낼 창구가 자리를 잡았습니다."
- 시점·계절 수식어는 **진짜 어울릴 때만** 곁들이고, 매 판마다 깔지 않습니다. (아래 안티패턴 「시점 강박」·「같은 모티프 반복」 참고)
- 도착 선언 예: "…, 자리를 잡았습니다.", "…, 새로 꾸몄습니다.", "…한 손질이 다녀갔습니다.", "…한 업데이트가 고개를 들이밀었습니다."

### 크기에 맞춰 무게를 조절합니다 (SemVer)

업데이트의 무게와 인용문의 무게가 어긋나면 안 됩니다. 어떤 버전을 올렸는지로 결을 고릅니다.

| 변경 유형 | 인용문 무게 | 도착 선언 결 | 도착 선언 예 |
|---|---|---|---|
| **PATCH** (내부 수정·소소한 손질) | 가볍게, 슬며시 | "깨알같은", "조용히", "슬쩍" | "깨알같은 손질이 슬쩍 다녀갔습니다.", "조용히 자리를 바로잡았습니다." |
| **MINOR** (기능 추가·UI 변경) | 반갑게, 또렷이 | "기분 좋게", "새로" | "○○가 자리를 잡았습니다.", "○○를 새로 열었습니다." |
| **MAJOR** (정식판·도메인 변경) | 묵직하게, 한 획 | "마침내", "한 획" | "마침내 ○○가 술독을 열고 나왔습니다.", "한 시대를 여는 정식판이 당도하였습니다." |

PATCH에 "마침내·한 시대"는 허풍이고, MAJOR에 "슬쩍·깨알"은 과한 겸손입니다. 크기는 부풀리지도 깎지도 않습니다.

## 철칙: 시점·계절은 *선택*이지만, 담는다면 *사실*이어야 한다

시점·계절은 **필수가 아니라 선택적 양념**입니다. 안 넣어도 좋은 인용문이 되고, 내용이 약한데 계절로 분량만 채우면 오히려 밋밋해집니다. 다만 **넣기로 했다면, 그 시간·계절·날씨·절기는 반드시 진짜 릴리즈 시점과 일치**해야 합니다. 6월인데 "동짓날", 한낮인데 "자정", 맑은 날인데 "눈보라"는 전부 금지입니다. 거짓 정경은 재미가 아니라 거짓말이고, 읽는 사람이 바로 알아챕니다.

**같은 시기에 여러 판을 낸다면 같은 절기를 반복하지 마세요.** 며칠 새 여러 릴리즈가 전부 "하지"로 시작하면 식상합니다. 시점은 빼거나, 시각대(아침·한낮·밤)·발효 상태로 변주하거나, 아예 내용만으로 승부합니다.

**양념을 칠 거라면 먼저 실제 정황부터 확인하세요:**

- **오늘 날짜** — 시스템 날짜 또는 해당 버전의 git 커밋 시각(`git log -1 --format=%ci <범프커밋>`).
- **대략의 시각** — 새벽 / 아침 / 한낮 / 해질녘 / 밤 / 자정. (커밋 시각으로 추정)
- **계절** — 봄/여름/가을/겨울, 그리고 장마·삼복·꽃샘추위 같은 한국적 절기 감각.
- **가장 가까운 절기** — 아래 표에서 날짜로 고릅니다. 절기 하루 전후면 "○○를 하루 앞둔" 같은 훅이 좋습니다.

그 다음 그 정경을 양조의 세계로 번역합니다. **발효는 계절을 탑니다** — 한여름엔 발효가 폭주해 관리가 까다롭고, 한겨울엔 더디게 익습니다. 이런 실제 양조 상식도 좋은 재료입니다.

## 변경 항목 도출

멋부리기 전에 **실제로 무엇이 바뀌었는지** 정확히 파악합니다.

- 버전 범위의 커밋·디프를 봅니다: `git log <이전태그>..<현재> --oneline`, `git diff --stat …`.
- **사용자가 체감할 변화** 위주로 불릿을 뽑습니다(디자인·기능·동작). 내부 리팩토링·빌드 잡일은 생략하거나 한 줄로 묶습니다.
- 불릿은 보통 2~6개. 각 불릿은 **굵은 라벨 + 한 줄 설명** 꼴이 읽기 좋습니다.

## 시각 변경은 before/after로 보여주기

로고·favicon·색·레이아웃처럼 **눈으로 보는 변경**은 글로만 적으면 와닿지 않습니다.
해당 항목엔 **before/after 이미지를 나란히** 넣습니다.

- 이미지는 리포에 커밋합니다(예: `apps/web/static/release/`, `docs/release/`).
  - **CHANGELOG.md**: 상대경로 `![…](./release/…png)` — GitHub이 파일 기준 상대경로를 렌더합니다.
  - **GitHub Release 본문**: `raw.githubusercontent.com/<owner>/<repo>/<ref>/…` 절대 URL — Release는 상대경로를 렌더하지 않습니다.
- before/after를 한 장에 나란히 합치거나 두 장을 연달아 둡니다.
- favicon·아이콘은 작은 크기(16px)도 함께 보여 가독성을 드러냅니다.

## 형식 템플릿

```markdown
## [버전] — YYYY-MM-DD

> *{업데이트 내용을 익살스럽게 알리는 도착 선언. 시점·계절은 어울릴 때만 곁들임. 버전 크기에 맞는 무게로. 이탤릭, 존댓말, 1~2문장.}*

- **{굵은 라벨}**: {무엇이 바뀌었는지 명확한 한 줄. 존댓말. em-dash 대신 콜론이나 문장으로 잇습니다.}
- **{굵은 라벨}**: {…}
```

라벨은 분류(추가/변경/수정)여도 좋고, 그 버전의 성격을 담은 표현("살아난 움직임", "새 활자")이어도 좋습니다. 명확함만 잃지 마세요.

## CHANGELOG 머리말 (파일 맨 위 고정)

서브프로젝트 이름만 바꿔 각 CHANGELOG 맨 위에 둡니다 (`web` · `extension` · `domain` · `design-system`).

```markdown
# 변경 이력 — 알콜미터 {서브프로젝트}

> 각 판(版)은 *이탤릭 인용문*으로 그날의 짧은 이야기를 연 뒤,
> 무엇이 바뀌었는지 또렷한 항목으로 잇습니다. — 양조장 밤일지 × 패치노트
```

## 예시 (좋은 톤 — web)

전면 리디자인(MINOR)을 낸 판입니다. **내용이 주인공이고, 시점은 곁들이지 않았습니다:**

```markdown
## [0.4.0] — 2026-06-20

> *표지를 통째로 새로 입은 측정 노트가 당도했습니다. 전 페이지에 차분한 먹빛과 붉은 불꽃 한 점, 또박또박 살아 숨 쉬는 숫자를 들였습니다.*

- **새 디자인 「측정 노트」**: 전 페이지에 차분한 먹빛과 단 한 점의 붉은 불꽃을 입혔습니다.
- **살아난 움직임**: 히어로엔 탄산이 피어오르고, 제목 아래 손그림 밑줄이 그어졌다 사라집니다.
- **새 활자**: 한글 Pretendard와, 계측기처럼 또박또박 읽히는 등폭 숫자를 들였습니다.
- **계기판 결과**: 막걸리 배합의 합계·예상 도수를 붉게 또렷이 새겼습니다.
- **한 권으로 통일**: 홈·FAQ·개인정보까지 같은 손끝으로 정리하였습니다.
```

왜 좋은가: 인용문이 *무엇이 바뀌었는지*(차림새가 통째로)부터 위트 있게 꺼내고, "당도했습니다"로 도착을 선언하며(UI 변경이라 MINOR 무게), 존댓말입니다. 계절을 억지로 깔지 않았고, em-dash도 없습니다. 시점을 곁들이고 싶었다면 "푹푹 찌는 한낮에" 정도를 *뒤에* 살짝 얹는 선에서 그칩니다.

## 안티패턴 (이러면 실패)

- **거짓 정경**: 실제와 다른 시간·계절·절기·날씨. (이 스킬을 만든 이유가 이걸 막으려는 것입니다.)
- **도착을 안 알리는 서정 묘사**: 계절 풍경만 그리다 끝내 *업데이트가 왔다*는 신호가 없는 인용문. 반드시 "찾아왔습니다 / 맞이합니다 / 고개를 들이밀었습니다" 류로 착지합니다.
- **시점 강박**: 매 판을 계절·절기 수식어로 시작하기. 시점은 선택적 양념이고, 주인공은 변경 내용입니다. 안 어울리면 뺍니다.
- **같은 모티프 반복**: 며칠 새 여러 판이 같은 절기·시각을 반복 인용(예: 전부 "하지"). 가까운 판끼리는 시점을 빼거나 다른 결(시각대·발효 상태)로 변주합니다.
- **크기와 안 맞는 무게**: PATCH를 "마침내·한 시대"로 부풀리거나 MAJOR를 "슬쩍·깨알"로 축소하지 않습니다. 버전 크기에 결을 맞춥니다.
- **불릿·인용문의 em-dash(—)**: 라벨은 콜론이나 문장으로, 부연·이유는 접속사(왜냐하면·그리고)로 풉니다.
- **반말**: "…했다." 한 군데라도 섞이면 톤이 깨집니다.
- **정보 없는 미스터리 불릿**: "무언가 더 좋아졌습니다" 류. 멋만 있고 변경 내용이 없으면 변경 이력이 아닙니다.
- **과한 산문**: 인용문이 한 문단을 넘기거나 형용사가 폭주하면 오히려 안 읽힙니다. 1~2문장.
- **이모지 남발**: 톤은 활자로 만듭니다. 이모지는 0~1개.
- **chore만 나열**: 버전 범프·빌드 설정만 있는 항목은 사용자에게 의미 없습니다. (이런 변경뿐이면 항목을 만들 필요도, 인용문을 지어낼 필요도 없습니다.)

## 작업 순서 요약

1. 버전·변경점 파악 (`git log`/`diff`).
2. 그 변경을 **익살스럽게 전하는 도착 선언**을 인용문의 뼈대로 잡습니다(내용이 주인공). 진지한 문장에 피식 나는 건조한 위트 한 끗, 버전 크기(PATCH/MINOR/MAJOR)에 무게를 맞춥니다.
3. 시점·계절 양념은 **어울릴 때만** 곁들입니다. 곁들인다면 실제 릴리즈 시점과 일치하고, 가까운 판끼리 같은 절기를 반복하지 않습니다.
4. 사용자 체감 변화 위주로 **명확한 불릿**(존댓말) 작성.
5. 해당 서브프로젝트의 CHANGELOG(예: `apps/web/CHANGELOG.md`) 맨 위(머리말 아래)에 끼워 넣습니다.
